Below is a detailed logic analysis for the FactOptimizer module, which is responsible for reducing the input fact set before handing it off to the DatalogSolver. This analysis considers the paper’s guidelines (e.g., “omit unused facts,” “collapse chains of direct casts,” “merge equivalent type/context pairs”) as well as our design and configuration. The following points outline the planned algorithm and implementation steps for FactOptimizer:

──────────────────────────────
1. Input and Data Organization
──────────────────────────────
• The optimizer receives a list of Fact objects. Each Fact has:
 – An identifier (id)
 – A fact_type (e.g., "TypeContextPair", "Cast", "FunctionPointer", "ICall", "PointsTo", etc.)
 – A data dictionary containing the fact’s content (for example, for a Cast fact, keys could be "src" and "dest"; for a TypeContextPair, keys might be "type" and "context").
• The optimizer should first index the facts by their id (e.g., using a dictionary) to efficiently look up and update dependencies.

──────────────────────────────
2. Merging of Redundant Facts
──────────────────────────────
A key optimization is to merge facts that are equivalent. In particular:
 a. TypeContextPair Merging
  – Check for reciprocal Cast facts. If there is a Cast fact from fact A to fact B (i.e., Cast(A, B)) and also a Cast fact Cast(B, A), then the two TypeContextPair facts underlying A and B are equivalent and can be merged.
  – Choose a canonical representative (for example, the one with the lower id) to represent the merged pair.
  – Update all other facts that refer to the non-canonical id so that they now reference the canonical id.
 b. Duplicate Facts
  – For any two facts that are identical (same fact_type and same data), remove duplicates so that only one instance remains.

──────────────────────────────
3. Collapsing Cast Chains
──────────────────────────────
Indirect type propagation may be recorded as a chain of successive Cast facts. To simplify the fact set:
 a. Build a directed “cast graph” where each node is a fact id (typically from a TypeContextPair) and each edge represents a Cast fact (edge from “src” to “dest”).
 b. For every node, compute the transitive closure (using DFS or BFS) so that you know all reachable nodes from a given source.
 c. For a chain like Cast(n1, n2) followed by Cast(n2, n3), if there is no “branching” (i.e., the value is propagated uniquely without ambiguity), then the chain can be “collapsed” into a single Cast(n1, n3) fact.
 d. As an additional optimization, perform a transitive reduction of the cast graph so that redundant intermediate edges are removed. (For example, if n1 reaches n3 via a 2–step chain, and if that same pair (n1, n3) is already represented directly, then the intermediate Cast(n1, n2) coupled with Cast(n2, n3) may be considered redundant.)
 e. Note that collapsing chains must preserve the semantics required by the target-set computation so that no valid propagation path is lost.

──────────────────────────────
4. Pruning Unused Facts
──────────────────────────────
Not every extracted fact is used in other relations—and some may be entirely superfluous:
 a. Identify “root” or “primary” facts that the Datalog rules require. These typically include:
  – Facts of type FunctionPointer, ICall, and any Fact that is used as the starting point for a propagation (e.g., type information used in a Cast).
 b. For each fact (especially TypeContextPair), scan the data dictionaries of all other facts. For instance, in Cast facts the keys “src” and “dest” refer to type/context identifiers. If a TypeContextPair fact’s id is never used in any other fact’s data (or is not referenced by any Datalog rule as a starting or ending point), then it can be pruned.
 c. Build a “used” set by iterating over all facts and collecting every fact id that appears as:
  – The value for keys like “src”, “dest” in Cast;
  – References in PointsTo, StructMember, UnionMember, etc.
 d. Remove all facts with types that are not in this “used” set, except for those that are considered roots (because they come from external inputs or are needed for output).

──────────────────────────────
5. Updating References After Optimization
──────────────────────────────
Once merging and chain-collapsing operations are performed, all fact references must be updated accordingly:
 a. When two TypeContextPair facts are merged, all occurrences of the “old” id in any related fact (e.g., Cast, PointsTo) must be replaced by the canonical id.
 b. Similarly, if certain Cast facts are removed (because they are redundant due to transitive closure), ensure that any solver input that expected a direct cast uses the updated, collapsed fact.
 c. This update step guarantees that the final fact set is self-consistent and that no “dangling” references remain.

──────────────────────────────
6. Handling Special Cases
──────────────────────────────
• Skip Primitive C Types:
 – As outlined in the paper, facts referring to primitive types (e.g., char, void) that are smaller than a pointer can be ignored—unless they are relevant as void* (which has the same size). This is to avoid including irrelevant type propagation facts.
• Inline Assembly and Non-standard AST Nodes:
 – Although the treatment of inline assembly is outside the main scope, any fact whose extraction is ambiguous (or not referenced later) may be pruned.
• Dynamic Linking Considerations:
 – The optimizer should ensure that any “external” facts (those that will later appear in module summaries and be used by the runtime enforcer) are preserved. For facts marked for dynamic linking (as indicated by extra fields or fact_type markers), do not prune them even if they appear unreferenced locally.

──────────────────────────────
7. Output
──────────────────────────────
• The optimized fact set is returned as a List of Fact objects.
• The final output should be significantly smaller (fewer redundant or chained facts) so that when the fact set is passed to Soufflé in the DatalogSolver module, the solver’s workload is minimized.
• The transformed fact set must maintain all information needed to compute the TargetSet relation accurately according to the propagation rules described in the paper (rules (T), (P), (S), (U), (F1), (F2), (IC1), (IC2)).

──────────────────────────────
8. Summary of the Optimizer’s Steps
──────────────────────────────
1. Build an index of facts (id → Fact) for quick lookups.
2. Identify and merge duplicate or equivalent TypeContextPair facts by detecting reciprocal Cast relationships.
3. Construct a cast graph from Cast facts, compute transitive closure, and collapse chains into minimal direct edges (using transitive reduction if possible).
4. Prune facts that are not referenced by any other fact except for “root” facts.
5. Update all dependent facts to point to canonical identifiers after merges.
6. Return the final, optimized list of Facts for further processing.

──────────────────────────────
9. Integration Notes (Based on Configuration)
──────────────────────────────
• Our configuration (from config.yaml) does not affect the logic of fact optimization directly (since training parameters are not applicable), but note that dynamic linking is enabled, so any fact marked for external use or module summaries must be preserved.
• The FactOptimizer module must output the optimized facts in the same consistent format that will be used by DatalogSolver.
• Logging or debugging prints (using our shared utils or configuration settings) should be added so that during development, the reduction in fact count and changes to cast chains can be verified.

By following these steps and ensuring that all references remain consistent, the FactOptimizer module will reduce the size and complexity of the fact input without sacrificing the correctness needed for computing precise TargetSet relations in the TyPro system.

This thorough analysis should guide the subsequent code implementation in fact_optimizer.py without deviating from the design and methodology described in the paper.
