2. Methodology Reproduction
──────────────────────────────
A. Fact Extraction from the Clang AST  
  • Modify Clang’s front-end so that when parsing C code, it traverses the AST and extracts the following “facts”:  
   – Type and Context Pairs:  
     ○ For every expression in a function, capture a pair (type, context) and assign a unique identifier. (E.g., TypeContextPair(n, t, c)).  
    ○ Also record global variables (as context) and function declarations (return and parameter types).  
  • Type Constructs:  
   – For pointer types, extract and store the pointee type (via a PointsTo relation).  
   – For compound types like structures and unions, record fields using relations such as StructMember (with byte offset) and UnionMember (with field type).  
  • Casts & Transfers:  
   – For every cast (explicit or implicit), record a fact in the form Cast(n_src, n_dest) indicating type propagation across casts.  
   – This should cover casts between function pointer types as well as propagations happening as parameters are passed into functions or from indirect call arguments (and return types, if used).

  • Function Pointers & Indirect Calls:  
   – Identify all “address-taken” functions by detecting expressions such as &f outside direct calls. Create facts like FunctionPointer(n, f, num_args, is_vararg).  
   – For every indirect call (e.g., e′(a1, …, am)), record ICall(N(e′), call_expression, m) along with a separate TypeCall fact that records the type expected (but note that for indirect calls the context may be approximated).  

B. Fact Aggregation and Optimizations  
  • Merge all fact sets coming from different compilation units (source files).  
  • Implement optimizations such as:  
   – Omit TypeContextPair facts that are not referenced in any other relation (to reduce the size of the fact base).  
   – Skip primitive C types (e.g., char, void) that are not relevant for function pointer propagation.  
   – Collapse chains of direct casts as described (e.g. handling “(fptr_int)((void*)&f1)” as one direct cast).  
   – Merge equivalent type/context pairs when reciprocal Cast facts exist (as outlined in the optimizations section).

C. Datalog Analysis (Type Propagation & Target Set Computation)  
  • Encode the propagation rules as Horn clauses in the datalog language. The key groups of rules are:
   1. Propagation rules:  
    – Rule (T): Transitive propagation across multiple casts.  
    – Rule (P): Pointer aliasing (bidirectional propagation when pointers get cast).  
    – Rules (S) and (U): Propagate types through structure and union fields.
   2. Target Set rules:  
    – Rule (F1) for fixed-arity functions and rule (F2) for variadic functions. These rules use the computed Cast relation to “connect” the type of an indirect call site with function pointer types that have the correct arg-count.  
   3. Indirect call context transfer (IC1 and IC2):  
    – To cover cases where the arguments’ or return types’ contexts matter, add rules that simulate context transfer from the caller to the potential callee.
  • Feed the merged and optimized fact set into Soufflé along with your Horn clause rules.  
  • Run the solver until no new facts in the TargetSet(n_call, f) relation are derived. This final relation represents the allowed function targets for every indirect call.

D. Code Transformation & Enforcement  
  • Instrument the LLVM code-generation phase:  
   – Modify or add a pass that replaces every indirect function call with a switch-case construct.
   – Each case in the switch corresponds to one valid target (as computed in the TargetSet relation) and makes a direct call using the function’s unique identifier.
   – In the default case (i.e., if the identifier does not match any target), insert code to terminate the program immediately.
  • For address-taken functions, replace function pointers in memory with a unique function identifier.  
  • Ensure that your transformation yields a binary that enforces the forward CFI policy without runtime overhead (apart from the negligible cost from the switch-case structure).

E. Dynamic Linking Support (Advanced Component)  
  • Implement module summary generation:  
   – For each module, export the “external” facts (those that might be visible across module boundaries) using additional relations (ExternalSymbol, InterfaceType, etc.) as described in the paper’s Appendix B.  
  • At runtime, build a runtime library (in C++) that loads these module summaries and re-runs the target set computation if new modules are loaded.  
  • Use just-in-time techniques to recompile new switch-case constructs when the target sets expand due to dynamic loading.  
  • (NOTE: The precise integration of the summary and JIT compilation may require further design iterations as the paper’s description is high level; document your assumptions as you implement.)
