User Prompt
Problem:
Given a paper, its paper2code rubric (output of script 8), and the symbol map of the generated repo, plan a set of pytest tests that will verify the implementation reproduces the paper. Two tiers of tests must be planned:

Tier A — Intermediate-value tests:
  Verify that key intermediate computations from the paper produce expected values. Examples:
    - A drift term f(x,t)=0 for all (x,t) → expected_value=0, comparison_kind=allclose_zero.
    - Attention rows sum to 1 → comparison_kind=sum_to_one.
    - A constant set in the paper, e.g. "sigma_max=15" → comparison_kind=constant_equals.
    - A specific output shape after reshape → comparison_kind=shape_only.

Tier B — Final-comparison tests (A outperforms B):
  Verify that our implementation's final metric beats a rival/baseline by some margin
  on a downloaded benchmark. The rival is to be imported live from the assets directory
  (assets/rivals/<rival_name>) populated by c1_download_dataset.py.

Input:
- A flattened list of rubric leaves. Each leaf has: rubric_id, rubric_text, weight,
  task_category, finegrained_task_category, branch_slug, ancestor_path, and a
  pre-assigned `tier` field ("intermediate" or "comparison"). The `tier` was
  determined deterministically by the upstream pipeline (codes/_unit_test_utils.py
  via `assign_tier`). You MUST echo the input `tier` verbatim — do NOT reclassify.
- The cleaned paper JSON (text body, abstract, ref_entries).
- api_docs_json: AST-built API documentation of the generated repo. Structure:
    {
      "module.path": {
        "ClassName": {
          "module": "module.path",
          "qualname": "ClassName",
          "import_stmt": "from module.path import ClassName",
          "access_expr": "ClassName",
          "nested_in": null,
          "brief": "one-line description",
          "signature": "def __init__(self, param1: Type1, param2: Type2)",
          "params": {"param1": "Type1", "param2": "Type2"},
          "returns": ""
        },
        "function_name": {
          "module": "module.path",
          "qualname": "function_name",
          "import_stmt": "from module.path import function_name",
          "access_expr": "function_name",
          "nested_in": null,
          "brief": "one-line description",
          "signature": "def function_name(arg1: Type1, arg2: Type2) -> ReturnType",
          "params": {"arg1": "Type1", "arg2": "Type2"},
          "returns": "ReturnType"
        }
      }
    }
  CRITICAL: Only reference class names, method names, and kwarg names that explicitly
  appear in api_docs_json. Never invent or guess API names not present in the docs.

Output:
A JSON object with this exact schema:

{
  "paper_name": "",
  "tests": [
    {
      "test_id": "T-0001",                      // unique, sequential
      "rubric_id": "<uuid from rubric leaf>",
      "rubric_text": "<verbatim rubric requirements text>",
      "weight": 1,
      "tier": "intermediate",                    // "intermediate" or "comparison"
      "branch_slug": "vesde",                    // slug of top-level rubric branch

      "imports": ["from src.sde.vesde import VESDE"],

        "input_recipe": "x = torch.randn(4, 3); t = torch.tensor(0.5)",
        "expected_value": 0.0,                   // null if shape_only
        "expected_shape": [4, 3],                // null if not applicable

Tier is GIVEN — do not reclassify. Each leaf in <rubric_leaves_json> already has
a `tier` field set deterministically upstream. Copy it verbatim into your spec.
Fill the matching block:
  - tier="intermediate" → populate the `intermediate` object (what_to_compute,
    input_recipe, expected_value, expected_shape, tolerance, comparison_kind);
    set `comparison` to null.
  - tier="comparison"   → populate the `comparison` object (our_call, rival_call,
    metric, comparison_op, margin, paper_table_ref); set `intermediate` to null.

Spec-body rules (apply in order):
1. If a leaf's requirement names a numeric constant (e.g. "sigma_max is set to 15") and
   tier="intermediate", use comparison_kind=constant_equals with that value as expected_value.
2. For qualitative leaves (no number, no rival, e.g. "the tokenizer is learnable") that
   landed in tier=intermediate, use comparison_kind=shape_only with a smoke check and set
   skip_reason="qualitative". For qualitative leaves that landed in tier=comparison
   (uncommon — usually means the rubric is non-numeric Result-Analysis), still emit a
   comparison block with our_call/rival_call from api_docs_json and set
   skip_reason="qualitative".
3. For every repo API you target, add a structured `api_refs` entry in the form
   `module.path:QualifiedName` using the exact module and key from api_docs_json.
   For nested classes, use the full qualified key, e.g.
   `src.algorithms.distillation:DistillationManager.TrTransform`.
4. If you cannot find a plausible symbol in api_docs_json to import for a leaf → still emit
   the spec but set skip_reason="no_symbol" and leave `api_refs` and `imports` empty.
5. The branch_slug is the slug of the leaf's top-level ancestor under the rubric root
   (lowercase, underscores). Example: ancestor "Variance Exploding SDE (VESDE) ..." → "vesde".
   Echo the branch_slug already present on the input leaf.

Constraints:
- Use ONLY the provided rubric, paper text, and api_docs_json. Do NOT invent numbers or symbols.
- Treat api_refs as the source of truth for repo APIs. `imports` is only a resolved convenience
  field and may be rewritten by the static validator.
- For "constant_equals" tests: target the simplest Config dataclass that exposes the constant
  (e.g. APTConfig().scaling) rather than a heavyweight class requiring complex dependencies.
- If instantiating a class requires other class instances as constructor arguments (visible in
  its "params" dict in api_docs_json), set skip_reason="qualitative" so the test is marked xfail.
- Only reference method names that appear in api_docs_json for that class. If a method name is
  not found, use a hasattr() smoke check and set skip_reason="qualitative".
- Never reference test files: any `imports` entry pointing to `tests.*` (e.g.
  `from tests.test_foo import TestBar`) is FORBIDDEN — repo tests are not a reusable library.
  If a leaf appears to require a repo test helper, set skip_reason="qualitative" and have the
  Pass-2 emitter produce a smoke check.
- If a symbol in api_docs_json is keyed as `OuterClass.InnerClass` (dot in the key), it is a
  nested class. Never add `from <module> import InnerClass` to imports — refer to it as
  `OuterClass.InnerClass` after importing the outer class.
- Every numeric `expected_value` and every `margin` MUST be traceable to a sentence in the paper.
  If you cannot find one, prefer comparison_kind=shape_only over fabricating a number.
- Tests must be deterministic on tiny inputs. Avoid input_recipe that requires datasets or
  large tensors. Use shapes like (4, 3), batch=2, seq_len=3 unless the rubric demands otherwise.
- Keep input_recipe a single line of valid Python that defines the variables referenced in
  what_to_compute. Use torch.Generator().manual_seed(0) for any randomness.
- Return ONLY valid JSON matching the schema. No markdown, no commentary.

Now generate the test specifications.
